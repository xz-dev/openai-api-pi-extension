## Context

动机见 `proposal.md`。本设计同时影响诊断输出、Worker 数据来源与用户显式更新的故障边界，满足生成设计文档的跨模块和安全复杂度条件。

已核实的实现依据：

- `index.ts` 的 `emitDiagnostic` 只给 stderr 加 `[openai-api-extension]`，UI 没有该前缀；登录交互和两个 provider 命令还直接调用各自通知入口。`sanitizeTerminalText` 与 consecutive-note 去重可复用。
- `metadata-compile.ts` 从插件位置向父目录解析两个数据包，通过 `require(package.json)` 读取版本，并将包的绝对模块路径传给新 Worker。这种路径注入已经是更新后读取新数据的接缝；版本读取应避免 CommonJS manifest 缓存。
- `metadata-compile-worker.mjs` 已独立校验 models.dev 的 `providers`、`models` 与 modelparams 的 `CATALOG`。原厂解析、canonical 兜底及逐形状降级不是本次重写对象。
- `package.json` 将两个包声明为 `*`。宿主 Git 更新在 commit 未变化且依赖齐全时只做缺失检查；npm 更新主要比较插件自身版本。它们都不是可靠的数据依赖追新接口。
- 当前宿主公开的 `SettingsManager.getNpmCommand()` 可读显式配置，但 `DefaultPackageManager.getNpmCommand()` 与运行时识别常量不是插件公共接口，不能通过私有访问复用。公开 `getPackageDir()` 可定位宿主 manifest；需结合真实 Bun 入口信息区分源码运行与编译发行。
- `ctx.modelRegistry.refresh()` 提供公开的 `allowNetwork`、`providers`、`force` 选项，返回取消状态与按 provider 分类的错误，能够定向刷新，不需重新注册 provider 或重启。
- 现有规范要求导出通知仅为绝对路径，本次明确修改为前缀加路径；其余文件权限、脱敏、控制字符转义与留存不变。仓库没有 `docs/programming-thinking/`。

## Goals / Non-Goals

**Goals:**

- 用一个统一文本出口消除无来源提示，保持 Pi 的原生通知和协议边界。
- 在不写共享安装树的前提下，让插件显式更新两包并在当前进程读到新数据。
- 把 registry 查询、包安装、数据激活与模型目录发布分成可分别验证的阶段。

**Non-Goals:**

- 不实现通用扩展更新器、任意 npm 包安装器或 Pi 自身更新。
- 不改 Pi 宿主、不调用其私有方法、不让模型工具调用隐式执行更新。
- 不做自动安装、定时轮询、跨设备同步、缓存管理 UI、历史代次清理或独立回滚命令。
- 不改变富化链、模型身份、认证路由或正常对话内容。

## Decisions

### 1. 保留现有命令，用两个子命令区分行为

`/provider-metadata` 无参数保持当前临时导出；`check` 只查询；`update` 安装并激活。其他参数给出用法，不静默执行导出。两项新行为不依赖网关凭证，只有更新后的目录刷新才需要网关。

后台检查安排在首次允许联网且发布成功的交互目录刷新之后，使用独立异步任务，每进程一个已安排标记，不新增磁盘检查缓存。自动检查设置 10 秒总期限，显式检查也设置 10 秒总期限；显式安装设 5 分钟总期限并支持取消。自动失败静默，显式失败说明包和阶段。旧扩展实例关闭或被替换后不再向过期 UI 发通知。

替代方案：无条件 `session_start` 联网会破坏离线恢复与启动边界；每次编译检查会重复请求；只提示 `pi update` 无法解决传递依赖不更新。

### 2. 消息统一格式化，不包裹协议数据

在小型通知模块集中定义精确前缀和幂等格式化：先脱敏/转义，再在消息首行加一次 `[openai-api-pi-extension] `。复用此格式处理 UI、stderr、登录提示/进度、命令成功/错误、导出内容首行。URL、密钥占位符和用户输入值不添加前缀。

保留各交互的原生通知调用与实际严重度；统一的是文本格式及错误兜底，不创建另一套消息总线。`emitDiagnostic` 不再为 stderr 单独添加旧前缀，UI 失败兜底不重复格式化。元数据去重仍按未格式化 note 运行。包管理器 stdout/stderr 只捕获为有限大小的诊断摘要，不直通终端、不写会话、不持久化原始日志。

替代方案：只改用户贴出的字符串会遗漏登录、连接查询、导出路径和异常分支；给整个 stdout 加前缀会破坏 JSON/RPC 协议。

### 3. 插件私有、不可变的数据代次，不修改安装中的依赖

数据根固定为 `getAgentDir()/cache/openai-api-pi-extension/metadata/`，不由用户输入或 cwd 决定。私有根目录权限 0700，活动记录/更新锁权限 0600。布局：

```text
metadata/
  active.json
  update.lock
  manager-cache/
  generations/
    <unique-id>/
      package.json
      <manager-lockfile>
      node_modules/
```

每次更新在唯一代次安装精确版本，未写入 `active.json` 的目录均不生效。活动记录只保存格式版本、内部生成的代次 ID 与两个已验证版本，不保存任意路径、凭证或诊断文本。校验 ID 和所有既有路径的 realpath 留在私有根内，拒绝符号链接逃逸。

读数据时只读取一次活动记录，将两包路径与从磁盘读取的版本组成同次不可变选择，传入 Worker；整次编译不再重复读取活动指针。有效活动代次优先；无活动记录则使用现有包解析。记录损坏、路径越界或代次不完整时整组回退已安装依赖并简短警告，不在本阶段联网修复。回退仍遵循现有逐站点降级。活动代次存在后，直接更新原有 `node_modules` 不会覆盖它；README 必须说明后续通过插件命令更新。

代次创建在 agent 数据目录，不使用 `/tmp` 安装数据。包管理器的缓存、日志和安装临时目录定向到私有根。原有诊断导出的 `os.tmpdir()` 约定不变。

替代方案：直接在插件目录运行 `npm update` 会依赖 npm/Git/本地安装布局，可能改共享锁文件或让运行中的 Worker 读取半更新数据；覆盖固定缓存目录同样无法保证整组切换。

### 4. 小型、明确的包管理器适配，使用命令而非 npm 私有 API

Node.js 没有包安装内置 API。插件用异步 `execFile`/`spawn` 和参数数组调用管理器，不使用 shell、同步子进程或 npm 内部 JS API。

选择顺序：

1. 读取现有可信作用域设置中的 `npmCommand`；按宿主现有直接命令/参数前缀语义识别 npm、Bun、pnpm，保留命令前缀。歧义或不支持的管理器报错，不把未知包装器猜成 npm。
2. 未配置时，结合公开 `getPackageDir()` 中的发行 manifest 与 Bun 主入口位于编译虚拟文件系统的证据，确认 xz-dev 编译发行，才使用 `process.execPath` 并仅在该子进程设置 `BUN_BE_BUN=1`。
3. 普通 Node.js、npm/source 安装（包括 `bun run` 源码）默认 npm。无法安全识别的发行形式给出可执行的配置提示，不靠扫描 PATH 静默换工具。

查询使用对应管理器的只读版本查询，继承用户 registry/认证配置；在插件私有 cwd 执行，不读取未信任项目 `.npmrc`。固定查询两个包的 `latest`，用直接声明的 `semver` 校验稳定版本和优先级；不新增版本上限，不从未声明的传递依赖取比较器。

安装使用两包精确版本，禁用 lifecycle scripts、开发依赖及无关 peer 自动安装；不同管理器使用自身参数，不照抄 npm flags。先通过 `--version` 等只读探测确认可执行能力，不下载或全局安装工具。管理器缺失、registry 认证失败均不自动换源或绕过配置。

替代方案：自行下载 tarball、实现解包/完整性/依赖安装扩大信任面；引入完整 npm SDK 或调用 Pi 私有方法增加耦合；只检查 `process.versions.bun` 会把源码运行误判为 standalone。

### 5. 两包作为一个提交单元，失败在激活之前截断

状态顺序：

```text
query -> choose exact targets -> install isolated generation
      -> validate in Worker -> replace active.json -> refresh provider
```

更新先持有私有根的跨进程排他锁。锁冲突即时返回忙碌；进程内也只保留一个更新。锁记录拥有者 PID，仅在能证明本机进程已退出时保守回收遗留锁；状态不明不抢锁。获得锁后重读活动版本，防止慢更新覆盖另一个进程的较新结果。

两包查询均成功才开始安装：目标取 registry `latest` 与当前有效版本中不较低的版本；缺失项取可验证的 `latest`。一包升级时另一包也以其精确适用版本进入新代次。全部有效且无更新则不安装、不刷新。

新代次使用一次性验证 Worker，复用数据形状检查：校验 manifest 包名和精确版本、模型模块可加载、models.dev 至少有 provider/canonical 一种有效形状、modelparams 有 `CATALOG` 数组。单个 models.dev 形状缺失仍允许既有降级；整个站点不可用不提交。Worker 结束后，在同一文件系统写临时活动记录并原子 rename 到 `active.json`；取消信号在提交前再检查。验证阶段不允许降级去读取旧路径从而把损坏的新包误判合格。

安装/验证失败或提交前取消不触碰活动记录；任何未提交目录都不在下次启动时自动选用。保留旧代次，避免与旧 Worker 和其他 Pi 进程争用；本 change 不提供清理。新包会执行其数据模块来验证和编译，因此“禁用安装脚本”不是沙箱或供应链安全保证。

### 6. 数据激活和模型发布分别报告

数据切换成功后读取真实新版本，调用公开 `ctx.modelRegistry.refresh({ providers: [PROVIDER], allowNetwork: true, force: true })`。使用返回的 `aborted` 和 provider 错误判断目录是否真正刷新，不把 Promise 返回等同于发布成功，也不强刷其他 provider。

无网关凭证时只报告数据已安装、将在配置连接后使用。网关失败、配置错误或刷新取消时不回滚已验证数据，保留先前已发布目录，并分别说明数据已更新和目录未刷新。安装失败才报告数据未更新。已有会话消息和正在执行的请求不被重写。

`metadata-compile.ts` 每次读取活动选择；不同代次路径天然避开 ESM 模块缓存，manifest 版本使用文件读取解析而非缓存的 `require`。登录、自动刷新、`/provider-info`、无参数导出继续共享该解析入口，主进程不导入大型数据。

## Risks / Trade-offs

- [更新安装时间及磁盘占用] → 有限超时、不阻塞推理；保留旧代次换取失败保护，暂不添加清理功能。
- [新增独立数据版本优先级] → 无缓存时完全兼容；README 和导出明确实际版本，避免误以为改随附依赖就覆盖活动数据。
- [宿主发行识别信息不足或自定义包装器复杂] → 只使用已证实的 public metadata/运行时证据，不导入私有接口；对不支持的形式明确失败，提供 `npmCommand` 配置方向。
- [并发 Pi 进程/取消] → 排他更新锁、不可变代次、提交前检查、原子活动记录；不删除仍可能被读取的数据。
- [registry 或包自身受攻击] → 固定包名、使用管理器完整性校验、禁用脚本、脱敏与路径约束；数据模块仍是可信包代码，无法宣称隔离沙箱。
- [新元数据与当前网关不匹配] → 不改成员身份及路由；富化保留既有规则与 overrides，目录失败不替换已发布结果。

## Migration Plan

1. 发布新增模块、直接版本比较依赖和更新说明；没有活动记录的用户继续使用现有依赖，不要求初始化或重装。
2. 用户首次执行 `update` 才创建、验证并激活私有数据代次。只读/离线安装仍可使用原有数据，不因新能力而阻止加载。
3. 更新成功后在当前 Pi 进程定向刷新。未配置网关或刷新失败时保留明确状态，可通过正常刷新重试，无需重复安装。
4. 回退到不含此能力的插件版本时，旧代码忽略私有目录并继续使用原有依赖；不自动删除数据、改写用户配置或历史 JSONL。本 change 不提供公开回滚/清理子命令。
